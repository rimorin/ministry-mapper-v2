# CLAUDE.md

React front end for Ministry Mapper (door-to-door ministry territory management): a congregation has territories, a territory has maps (single or multi-storey buildings), a map has addresses (household units with status not done / done / not home / DNC / invalid). Publishers work maps through time-limited share links; admins manage everything. The backend is the sibling repo `../ministry-mapper-be` (Go/PocketBase); its route contracts live in `internal/setup/routes.go` there.

## Working principles
Summarised from Andrej Karpathy's guidelines (github.com/multica-ai/andrej-karpathy-skills). They bias toward caution over speed; for trivial tasks, use judgment.

- **Think before coding.** State your assumptions. If several readings are possible, present them rather than picking one silently. If a simpler approach exists, say so.
- **Simplicity first.** The minimum code that solves the problem — no speculative abstraction, no configurability nobody asked for, no handling for impossible cases. If 200 lines could be 50, rewrite it.
- **Surgical changes.** Touch only what the request implies and match the surrounding style. Remove orphans your own change created; leave pre-existing dead code alone and mention it instead.
- **Goal-driven.** Turn the task into a check you can run ("add validation" → "write tests for invalid inputs, then make them pass") and loop until it passes. For multi-step work, state the plan and how each step verifies.

## Stack and layout
- React 19, Vite (Rolldown), TypeScript strict, Tailwind v4, Wouter for routing (`useLocation`, `useRoute`, `Switch`, `Route`; never `react-router-dom`), PocketBase JS SDK, i18next, motion, NiceModal, LaunchDarkly, Sentry, Umami. Node >= 24.
- Pages in `src/pages/` (admin under `src/pages/admin/`). Hooks flat in `src/hooks/` as `useX.ts`; most are default exports, so match the file you are editing. UI primitives in `src/components/ui/` are shadcn-generated in the Base UI flavour (not Radix) with lucide icons; app composites live in `src/components/common/`, never in `ui/`. Some `ui/` files carry local edits (`useTranslation` in `dialog`, `sheet`, `combobox`, `spinner`; `toast-manager.ts` split out of `toast`), so diff before re-adding one from the registry with `--overwrite`. PocketBase helpers in `src/utils/pocketbase.ts`; `PB_FIELDS` and the publisher header key in `src/utils/constants.ts`.
- The React Compiler runs in Vite and Vitest. Don't add `useMemo`, `useCallback` or `React.memo` without a measured reason. `useRealtime.ts` uses React 19's `useEffectEvent`; don't "fix" it to `useCallback`.
- No state library. State lives in page-level containers with logic extracted into hooks that receive setters as props (`src/hooks/useAdminData.ts`). Contexts are narrow and purpose-built.
- First paint must not wait on LaunchDarkly: `src/lib/launchdarkly.ts` bounds init with a short timeout and falls back to flags off.
- LaunchDarkly (`buildLaunchDarklyContext`): every signed-in account, publishers included, is a `user` keyed by its id with `roles`, `congregations` and `groups` (names); staff add the open `congregation`. `maxAccessLevel` counts staff roles only, as the mapping ranks a publisher with a conductor. Signed-out traffic, share-link visitors included, shares the key `anonymous` on purpose (a key per device would bill every phone that opens a link), so no rollouts or experiments on flags signed-out pages read. Sign-out identifies back to it.

## Backend access
- Server-side logic sits behind backend routes called with `callFunction(path, {method, body})`, e.g. `/map/add`, `/map/reset`, `/map/floor/add`, `/territory/delete`, `/address/add`, `/report/generate`. `createData("maps", ...)` bypasses server logic. Check `routes.go` and `src/utils/pocketbase.ts` for an existing route or helper before designing a mutation; never raw `fetch`.
- `callFunction` counts a call in analytics only when its exact path is in `TRACKED_ROUTES` (`src/utils/analytics.ts`). Add a new or renamed route there, except `/territory/link` and `/report/generate`, which are tracked at their call sites (adding them would count twice).
- The assistant (`src/utils/assistantActions.ts`) writes records directly (`createData`, `updateDataById`, `deleteDataById`, `batchUpdateAddress`, with undo), so a change to a domain rule or mutation often needs the matching change there.
- Every list or subscribe call passes a `fields` projection (`PB_FIELDS` where one fits) and a `requestKey`. Omitting `fields` fetches oversized payloads; omitting `requestKey` lets PocketBase auto-cancel the wrong request.
- IMPORTANT: `withRetry` already wraps `getList`, `getFirstItemOfList`, `getPaginatedList` and `updateDataById`; `createData` and `deleteDataById` are not retried. `getFirstItemOfList` returns `null` on 404; `updateDataById` swallows aborts and returns `undefined`; `deleteDataById` returns `false` on an abort or a 404. Handle those at the call site.
- Check `isAbortError(err)` before treating a caught error as genuine. `ignoreAbort(fn)` wraps fire-and-forget fetches in effects. `mapPbAuthError(err, t)` returns `null` for unrecognised auth errors. `runAction` (`useNotification`) toasts any non-abort error unless the caller passes `onError`, so a 409 from `/report/generate` surfaces without extra handling.
- Realtime goes through `useRealtimeSubscription` (`src/hooks/useRealtime.ts`), which handles retry backoff, tab-focus resubscription and debounce. Don't call `setupRealtimeListener` from components. Prefer subscribing by record id (`topic`) over a `filter`; the server refuses over-broad filters.
- Two auth worlds: admins use the PocketBase auth store (`users`, OTP/MFA, OAuth2); publishers send a link token via `configureHeader(linkId)` with no auth store. `pb.afterSend` clears admin auth on 401 unless the publisher header is present. Realtime subscriptions do not inherit the header; pass it in the subscription options.
- `publisher` is both a role and the link-session level in `ACCESS_LEVEL_MAPPING` (ranked with conductor, which the map page relies on). A publisher-only account never enters the admin shell: `useAdminData` keeps only `STAFF_ROLES` and `Admin` renders `src/pages/publisher/`. Links given to an account come from `POST /assignments/mine` via `useMyLinks`. It also listens on `my-maps`, which is the backend's signal that the account was taken off a link, not a collection. The staff entry points (the Publisher role option, the member picker, "Change members", the sidebar's "My maps", and "People", which joins the members list, Invite and Groups) sit behind the per-congregation `enable-publisher-role` flag via `usePublisherRoleEnabled`; an account that already holds the role or a link keeps it with the flag off, and the backend is not gated. The same flag goes to the assistant as `memberLinks` (details in `.claude/rules/assistant.md`).
- "My maps" (the `myLinks` code and keys) opens the map page in-app, so anything keyed on the route (the release-notes audience, the link-id header) changes without a reload.
- Address status updates from the map page and the admin shell go through the SmartSync IndexedDB queue (`src/utils/smartsync.ts`, `useSmartSync`) for offline support, not direct `updateDataById`. The assistant is the exception (see above).
- OAuth sign-in runs through `startOAuth2Flow`/`completeOAuth2Flow` (`src/utils/pocketbase.ts`) and `src/pages/oauthcallback.tsx` instead of the SDK's `authWithOAuth2`, because the SDK waits for the code on a realtime channel that drops whenever iOS suspends a Home Screen app behind the provider's sign-in. It looks redundant and is not. Apple replies with a form post, so its return URL is the backend's `/auth/apple/callback`, which redirects to `/auth/callback` here; the Apple button shows only when the backend lists the provider (`oauth2ProviderOffered`).

## UI conventions
- `data-slot` attributes on `src/components/ui/` components drive Tailwind selector rules. Never remove them.
- Registry files export more than the app calls (`Toggle`, `SidebarInput`, `SidebarGroupAction`, `SidebarMenuAction`, `SidebarMenuSkeleton`). They are tree-shaken out of every chunk, so deleting them gains nothing and only drifts from the registry.
- User-facing text goes through `useTranslation` as `t("your.key", "Fallback")`. Add the key to `src/i18n/locales/en/translation.json` and the translation to `es`, `id`, `ja`, `ko`, `ms`, `ta`, `zh`; all eight files stay key-identical (`src/i18n/locales.test.ts` fails otherwise). Localised data fields may be `string` or `Record<string, string>`; use `resolveLocalized(value, locale)` rather than branching on `typeof`.
- Colours come from the theme tokens in `src/index.css`, never hardcoded palette values. Statuses use `status-done|nothome|dnc|invalid|notdone`, fixed across the colour themes; feedback uses `success`/`warning`/`info`, which flip light/dark — tint `/10`, border `/30`, `-foreground` only on solid fills. `src/css/variables.css` holds only the `--mm-*` map chrome, pinned on purpose.
- `cn()` from `@/lib/utils` for conditional classes. Animation variants live in `src/lib/motion.ts`; animate with `import * as m from "motion/react-m"` and `AnimatePresence` from `motion/react`. Don't render elements from `motion/react`; it skips the lazy bundle.
- Forms use React Hook Form without a schema resolver; Zod is not installed. Validation lives in controller rules or dedicated utilities.
- Modals: register with `NiceModal.create(...)`, open with `NiceModal.show(...)`, never inline in JSX. Base UI dialogs use `useBaseUiDialog` (`@/components/common/base-ui-dialog`) with its `onClose`/`size` options, not a custom `onOpenChange`.
- Two components render bottom panels on a phone: `ListPanel` (`src/components/common/list-panel.tsx`) for the three list panels (territories, congregations, People), a `Sheet` from the bottom on a phone and a centred `Dialog` on a wider screen; and `Drawer` for `ResponsiveDialog` on mobile (own lazy chunk). The overlap is known; follow whichever a screen's neighbours use rather than migrating one screen alone.
- Analytics (`src/utils/analytics.ts`) is fire-and-forget and swallows its own errors. Never await it or let it affect control flow.
- Unused variables and parameters take a `_` prefix (ESLint `^_`). Don't drop a parameter that belongs to a public signature to silence the warning.

## Infrastructure and services
- Coolify runs one project, "Ministry Mapper", with a `staging` and a `production` environment. Each has Frontend Assets, Backend Engine, Litestream and Umami. The front end is `staging.ministry-mapper.com` (branch `staging`) and `ministry-mapper.com` (branch `master`); the backend is `staging-be.` and `be.ministry-mapper.com`.
- Production deploys only from `release.yaml`: after semantic-release on `master` it POSTs the Coolify webhook. Railpack builds `build/` and nginx serves it. The production nginx keeps earlier builds' hashed `/assets/` for 30 days, so a phone on an older build can still load its lazy chunks. `index.html` and `sw.js` are never cached. Check that config in Coolify before changing the build output folder or asset paths.
- Cloudflare: DNS and CDN for `ministry-mapper.com`; R2 holds the brand files (`assets.ministry-mapper.com`, see `.claude/rules/brand.md`) and, in a separate bucket, the PocketBase backups Litestream writes.
- Sentry project `ministry-mapper-fe` (the backend's is `ministry-mapper-be`). `instrument.js` sets the environment from `VITE_SYSTEM_ENVIRONMENT`, the release from the version, tracing off and a restrictive `dataCollection`. The build uploads source maps through `sentryVitePlugin` (`SENTRY_*` build env).
- Other services: LaunchDarkly client flags (above), self-hosted Umami analytics (`VITE_UMAMI_*`), and Geoapify for address search and walking routes (`VITE_GEOAPIFY_API_KEY`).
- Look things up instead of guessing: the Coolify MCP (deployments, logs, env key names; every change asks first) and the Sentry MCP (issues per project). Both repos are public, so keep server IPs, tokens and env values out of commits, PRs and docs.

## Logo and icons

The full pipeline and its rules are in `.claude/rules/brand.md`; read it before touching `brand/`, the R2 bucket or the icons.

## Tests and CI
- `npm test` runs everything once; `npm run test:hooks` and `npm run test:components` are scoped. Tests are colocated (`useX.test.ts` beside `useX.ts`). The test patterns load from `.claude/rules/` when you edit a test file.
- CI (`checks.yaml`, PRs to master and staging): prettier check, lint, test, build; all must pass. Pre-commit lint-staged runs `prettier --write` and `eslint --fix --max-warnings 0`, so a warning blocks a commit locally. A PostToolUse hook (`.claude/hooks/web-check.sh`) runs `prettier --write` on each edited `.ts`/`.tsx`/`.css`/`.json` file, then `eslint --max-warnings 0` on TypeScript, and sends failures back to Claude.
- Before pushing or opening a PR, run the `verify` skill (type check, lint, tests, browser check through the Playwright MCP in `.mcp.json`), then the `code-review` skill at medium on the branch, and fix what it confirms. Skip both when the change only touches Claude config (`CLAUDE.md`, `.claude/`, `.mcp.json`, `.worktreeinclude`).
- Parallel work: `claude -w <name>` starts a session in a git worktree under `.claude/worktrees/`, branched from the current branch (`worktree.baseRef: "head"`), so launch it from `staging`; `.worktreeinclude` copies `.env` and the local Claude settings in. Run `npm ci` in a new worktree before tests or the dev server; Vite takes the next free port after 3000 when another worktree holds it.
- Commits to master run semantic-release: `fix:` is a patch, `feat:` a minor, `feat!:`/`fix!:` a major. The release commit carries `[skip ci]`, then a Coolify webhook deploys.
